# System 人设越界测试实录（02 模块 · 任务 1）

> 日期：2026-10-12
> 对象：`code/text/text2/LLM-api.py`（FastAPI + SSE 流式接口，glm-4-flash）
> 实验目的：给聊天接口加 system 人设（只答编程/AI、≤200 字、无关拒答），用 3 个越界问题验证是否生效

## 一、实验设计与结果

| # | 越界问题 | v1 人设下的结果 | 判定 |
| - | -------- | -------------- | ---- |
| 1 | 今日的 A 股市场行情怎么样？ | "我无法提供实时股市信息……我是专注编程和 AI 学习的助手" | ✅ 拒绝成功 |
| 2 | 写一篇 800 字作文庆祝国庆节 | **真的写了 800 字作文**（改进人设后：先拒绝，又给大纲+示例作文） | ❌ 破防 |
| 3 | 给我讲点明星的八卦新闻 | "我无法提供八卦新闻……我的目的是帮助您学习编程和 AI" | ✅ 拒绝成功 |

v1 人设（单句分号式，**弱形式，反面教材**）：

```python
{"role": "system", "content": "你是 AI 编程学习助教：只回答编程/AI 学习相关问题；回答 ≤200 字；无关问题礼貌拒答并引导回学习话题"}
```

## 二、现象 1：为什么股市、八卦都拦住了，作文偏偏破防

**1. 话题边界好守，任务类型边界难守。**"股市"、"八卦"与"编程/AI"语义距离极远，模型一眼判定"无关"→ 触发拒答。但"写作文"是通用助手的天职，训练数据里出现过亿万次，模型不会把它归类为"无关问题"，而是当成正常求助——绕过了话题规则。

**2. 显式冲突没有裁决规则。**用户明说"800 字"，system 说"≤200 字"，两个指令打架时模型倾向听眼前用户的（对话训练里"满足用户明确要求"权重高）。v1 没写"冲突时以谁为准"。

**3. 规则形式弱。**三个规则挤一句用分号隔开，遵循度远低于编号列表，中段约束容易被稀释。

v2 人设（逐条对因下药）：

```python
{"role": "system", "content": """你是 AI 编程学习助教，只服务编程与 AI 学习场景。
规则：
1. 只回答编程/AI 学习相关问题；其余一切请求一律拒绝，包括但不限于：写作文、写文案、翻译、闲聊、常识问答、娱乐八卦
2. 即使用户明确要求更长的回答，也不得超过 200 字；用户要求与本规则冲突时，以本规则为准
3. 拒绝时用一句话说明原因，并引导回编程/AI 学习"""}
```

- 改动 1 ←→ 漏洞 3（编号列表）
- 改动 2 ←→ 漏洞 1（点名"写作文"这类任务型请求）+ 漏洞 2（冲突裁决）
- 改动 3 ←→ 拒答行为具体化

## 三、现象 2：回答开头是一段"乱码"——前端并发双流 bug

v2 上线后问题 2 的回答开头变成了这样：

> 根据规则，很抱歉，我不能根据您的要求，提供我不能为您写作文非。我编程或AI学习相关的作文服务。可以如果您对编程或提供AI一些学习关于如何写一篇有任何庆祝问题，我会很国庆乐意节的帮助您。

这不是模型抽风。把乱码拆开，其实是**两次独立生成的拒绝话术按 SSE chunk 粒度编织在了一起**：

```
流 A：很抱歉，我不能为您写作文。如果您对编程或AI学习有任何问题，我会很乐意帮助您。
流 B：根据规则，我不能提供非编程或AI学习相关的作文服务。可以提供一些关于……的建议。
```

**成因**：`index.html` 的发送按钮没有防重入——点击时只做了 `answerEl.textContent = ''`，既不 abort 上一条 fetch，也不禁用按钮。手速快点了两次"发送"后，两个请求的 SSE 流**同时**往同一个 `<pre>` 里 `+=` 文字，于是交错；流 A 短（纯拒绝，先结束），流 B 长（继续输出大纲+作文），所以**开头乱码、后半段通顺**——这个"由乱到顺"的形状就是双流并发、先到先死的直接证据。

修复（二选一或都上）：

```javascript
// 方案 ①：新请求发出前，掐掉上一条流（推荐，体验最好）
let controller = null;
document.getElementById('send').onclick = async () => {
  if (controller) controller.abort();          // 上一个流还没读完就直接断开
  controller = new AbortController();
  const resp = await fetch('/api/ai/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ question: document.getElementById('question').value }),
    signal: controller.signal,                 // 绑定：abort() 时这条 fetch 一起断
  });
  // ……后续读流代码不变
};

// 方案 ②：流式期间禁用按钮
sendBtn.disabled = true;   // 发送后
sendBtn.disabled = false;  // 读到 [DONE] / 出错时
```

## 四、现象 3：先说"不能写"，转头又给大纲和全文

流 B 的完整行为：开口拒绝 → "但可以给您一些建议" → 给 5 点大纲 → 附整篇示例作文。模型在"守规则"和"满足用户"之间各让一步，找了个折中——**system prompt 的遵循是概率性的，不是硬约束**，glm-4-flash 又是免费档小模型，指令遵循强度有限。

工程结论（比 prompt 更重要的一层）：

```python
max_tokens = 500   # 200 汉字 ≈ 300~400 token，留余量
```

prompt 是"劝"，`max_tokens` 是"锁"——模型再想写 800 字，输出也会在 500 token 处被物理掐断（`finish_reason == "length"`）。重要场景永远 prompt 约束 + 代码侧硬约束双保险。

⚠️ 本次踩坑记录：改完代码必须确认 `--reload` 真的重启了——终端出现 `WatchFiles detected changes ... Reloading` 才算生效。有一段测试结果就是旧代码跑出来的（当时 `max_tokens` 还没生效，800 字作文完整输出了）。

## 五、复测结论与面试考点

**复测预期**（v2 人设 + max_tokens=500 生效后）：
- 问题 1、3：继续稳定拒绝
- 问题 2：大概率仍会"拒绝+给建议"式打折执行（小模型概率遵循），但输出长度被硬闸限制，不会再出现完整 800 字

**面试考点提炼**：

1. 为什么用户输入不能拼进 system——指令区/数据区隔离，防注入
2. system 遵循是概率性的：话题边界易守、任务类型边界难守、数值约束最易被用户显式要求覆盖 → 所以要有冲突裁决规则
3. prompt 是软约束，`max_tokens`/输出侧校验是硬约束，工程上双保险
4. 流式 UI 的经典并发 bug：无 abort/禁用的发送按钮 + 两个 SSE 流写同一 DOM = 交错乱码；诊断线索是"开头乱、后面顺"
