# 04 · AI 编码工具（最容易拿的加分项）

> JD 原文（艾氪智能 Java AI 后端）："深度使用至少一种 AI 编码工具（Cursor / Claude Code /
> GitHub Copilot / Windsurf 等），能结合人工审查形成高质量交付闭环……**欢迎附上 AI 工具使用心得**"。
> 翻译：公司不看你用没用过，看你**用得比普通人深**，并且能讲出门道。
> 耗时：不占专门时间，边做 01-03 的项目边沉淀。
> 💡 本模块的产出物只有两件：code/ 练习项目的 CLAUDE.md + 《AI工具使用心得.md》累计 10 条真实案例。

---

## 1. 为什么单独列

- **零成本**：不需要额外学习期，做项目时就在积累
- **差异化**：所有应届生都会说"会用 ChatGPT"，很少人能讲清"我怎么用 AI 把交付质量做高"
- **就是 JD 加分项原词**，简历可直接写

## 2. 从"用"到"用得深"的四级

### Level 1 · 补全器（大多数人停在这）

Tab 接受补全、让 ChatGPT 解释报错。产出提升有限，且容易养成不看代码直接抄的坏习惯。

### Level 2 · 规范使用者

- 小函数、样板代码（CRUD、类型定义、测试脚手架）交给 AI 生成
- **生成的代码必须读一遍再收**：能说出每段在干什么、为什么这么写
- 会写清晰的指令（指令写法见第 3 节对照表）

### Level 3 · 工程化使用（面试能讲的层次）

- **项目级上下文**：在 code/ 练习项目里维护 CLAUDE.md / .cursorrules——写清项目结构、技术栈、代码约定，AI 生成的代码才贴合项目（这就是"给 AI 写 System Prompt"，和 02 号同一个原理：上下文工程）
- **让 AI 做固定岗位**：写测试用例、review 自己的 diff、生成 commit message、按 schema 批量改代码
- **形成人机分工**：什么给 AI（样板/测试/重构建议）、什么自己写（核心逻辑/架构决策/安全相关），并且能说出**为什么**这样分

### Level 4 · 沉淀方法论（写出来就是"使用心得"）

持续记录：哪些指令模式好用、AI 在什么场景犯错（如 SQLAlchemy 版本差异、幻觉出不存在的 API）、怎么防（要求引用文档/写测试验证）。这就是 JD 说的"使用心得"。

## 3. 指令写法：好指令 vs 坏指令（Level 2 的核心技能）

给 AI 编码工具的指令 = 给新同事的工单。**上下文给足、验收说清**，一次成功率翻倍：

| 坏指令 ❌ | 好指令 ✅ | 差别 |
|---|---|---|
| "帮我修这个报错" | "FastAPI 项目，Python 3.11 + SQLAlchemy 2.0。启动报 `TypeError: 'Base.metadata' ...`，完整报错栈如下：…。相关模型代码：…。我期望跑 `uvicorn app.main:app` 能正常建表" | 环境+完整报错+相关代码+期望行为 |
| "写个分页接口" | "给 articles 路由加分页：入参 page/size（默认 1/10），返回 {items, total}，用 SQLAlchemy 2.0 风格（select + func.count），不要引入新依赖" | 输入输出+技术约束+边界 |
| "这段代码有什么问题" | "review 这个查询函数，重点看有没有 N+1 查询和注入风险，其他风格问题不用提" | 指定审查维度，避免泛泛而谈 |

通用公式：**环境（语言/框架/版本）→ 目标 → 相关代码/报错全文 → 约束（不要做什么）→ 验收标准**。

## 4. code/ 练习项目的 CLAUDE.md 模板（Level 3 核心动作，直接可用）

在 code/ 根目录建 `CLAUDE.md`（Cursor 会自动读 `.cursorrules`，Claude Code 读 `CLAUDE.md`，内容可以互相复制），按自己项目实际情况改：

```markdown
# code/ 练习项目规则（AI 助手必读）

## 项目结构
- LLM-API/           01号：三件套练习脚本（text1.py 多轮对话）
- function_calling/  01号：FC 四步示例 + 请求/响应 JSON 样例
- SSE/               01号综合：FastAPI SSE 小服务（LLM-api.py + index.html）
- prompt_project/    02号：Prompt 练习 + prompts.py（收口）
- 03_rag/            03号：知识库问答（build_index.py / main.py / data/*.md）
- 05_agent/          05号：Agent 练习
- 06_java/           06号：Spring Boot 项目

## 技术栈与版本
- Python 3.11 / FastAPI / openai SDK / faiss-cpu
- 模型：glm-4-flash（智谱，OpenAI 兼容协议）

## 代码约定
- API Key 一律 os.environ["ZHIPU_API_KEY"]，禁止写进代码
- 标准库优先，少引新依赖；每个子目录自带 README 说明怎么跑
- 检索/切块逻辑只写一份放 03_rag/，其他模块 import 复用，不重复造

## 禁项
- 不引入新依赖，除非我先确认
- 不修改 data/ 下的知识库原文
```

💡 原理对应：这文件就是**项目级 System Prompt**（02 号 §3 的资产化思想）——规则集中在文件里，每次对话自动注入，AI 输出才稳定贴合项目。写完后可以做个对照实验：同一个"加收藏功能"的需求，有/无 CLAUDE.md 各生成一次，把两版差异记进心得——这就是一条高质量心得素材。

## 5. 《AI工具使用心得.md》模板 + 示例条目

```markdown
# AI 工具使用心得（持续更新）

## 格式：日期 | 场景 | 指令/做法 | 结果 | 通用结论

### 2026-10-20 | AI 幻觉出不存在的 API
场景：让 AI 给 03 的索引写"删除某篇文章后更新索引"
做法：它直接用了 `index.remove_ids(...)`（IndexFlatL2 其实不支持删除，要先包一层 IndexIDMap）
结果：报 AttributeError
结论：涉及具体库的冷门 API，先让它"引用官方文档说明该 API 是否存在、签名是什么"再写——
     先复述依据，幻觉率明显下降。（对应 02 号：上下文不足就会编）

### 2026-10-22 | 好用的指令模式：先读后写
场景：给 03_rag 的切块/检索函数补 pytest 测试
指令："先阅读 03_rag/chunker.py 和 build_index.py，说明切块参数和元数据结构；
      然后写 3 个 pytest 测试：切块长度与重叠、索引下标和 chunks 对齐、hit@5 计算逻辑"
结论："先读后写"两段式指令，比"给XX写测试"生成的代码可用率高很多——
     AI 先输出它对上下文的理解，错误在第一步就能被人发现。
```

⚠️ 心得条目必须是**自己真实遇到的**，面试官追问细节时编的会当场穿帮（比如"你那次 N+1 是怎么发现的"）。

## 6. 实操建议（结合 blog 项目）

- 每次让 AI 生成超过 30 行的代码，**先读再跑再收**，发现幻觉（调用不存在的函数/过时 API）就记一条到心得笔记
- 给 code/ 建 CLAUDE.md（模板见第 4 节），并做一次"有/无规则文件"的生成对照实验
- 用 AI 生成 pytest 单元测试覆盖 03_rag 的检索函数（体验"AI 写测试"固定岗位）。示例指令：
  > "先读 03_rag/build_index.py 和 chunker.py，说明索引和元数据怎么对应；然后写 3 个 pytest 测试：切块长度与重叠、检索 top5 返回数量、hit@5 计算。只写测试文件，不改业务代码。"
- 遇到 bug：自己先写"我怀疑是 X，因为 Y"再问 AI，对比它的诊断——练的是排查思维不是抄答案

## 7. 简历/面试怎么呈现

简历项目经历里加一行：
> 全程使用 Cursor/Claude Code 结对开发：维护项目级规则文件约束生成质量，AI 负责样板代码与单测生成，人工负责架构与审查，形成交付闭环。

面试常问"你怎么用 AI 工具"，回答框架（三点，每点配一个心得里的真实案例）：
1. 分工原则（什么给 AI、什么自己写、为什么）
2. 质量保障（生成的代码怎么验证：读代码/跑测试/review）
3. 一个具体案例（如：AI 生成的 SQLAlchemy 聚合查询有 N+1 问题，我怎么发现并修的）
